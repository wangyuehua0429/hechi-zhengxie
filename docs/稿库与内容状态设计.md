# 河池政协网 · 后台稿库与内容状态设计

> 编制日期：2026 年 9 月 11 日
> 适用范围：政协主站内容管理后台（`/admin`），落地排期见文末“分期实施”。
> 现状依据：`cms_article.status` 目前只有三态（`draft` 草稿／`published` 已发布／`offline` 已下线），公开接口只出“已发布 + 公开范围”；权限表 `sys_role`／`sys_role_channel`、编校扩展表 `cms_article_proof`、操作日志 `sys_operation_log` 已建但尚未用起来。

## 1. 为什么要分稿库

政务网站的内容发布有三条硬要求：**责任到人**（谁写的、谁审的、谁发的）、**过程留痕**（每一步都能查到时间与操作人）、**可收可回**（发错了能撤，撤了要说得清）。只有“草稿／已发布／下线”三态时，会出现这些说不清的情况：

- 稿件写完了、交上去了、还没审，放在“草稿”里，别人不知道它在等谁；
- 审核没通过，退回给谁、为什么退回，没有地方记录；
- 发出去又撤下来，和“从来没发过”在库里长得一样，事后查不了；
- 删掉的稿件是真删，误删无法恢复。

因此把内容按**生命周期**分成若干稿库，每个库对应一个状态，库与库之间的移动就是一次可追溯的操作。

## 2. 稿库设计（7 个库）

| 序 | 稿库 | 状态值 | 含义 | 前台／接口可见 | 典型操作人 |
| --- | --- | --- | --- | --- | --- |
| 1 | 草稿库 | `draft` | 正在写、还没提交；可反复改 | 否 | 栏目编辑 |
| 2 | 待审库 | `pending` | 已提交，等审核；写稿人只读 | 否 | 编辑提交，审核人处理 |
| 3 | 退回库 | `rejected` | 审核未通过，附退回意见 | 否 | 审核人退回，编辑修改 |
| 4 | 已发布库 | `published` | 对外正式发布 | **是** | 发布人（值班） |
| 5 | 已撤回库 | `withdrawn` | 曾发布，后被撤下；内容保留 | 否 | 发布人 |
| 6 | 归档库 | `archived` | 年限外只后台留存（复用 `public_scope=archive`，不改状态） | 否 | 系统按年限自动 |
| 7 | 回收站 | `deleted` | 软删除，可恢复 | 否 | 有删除权限者 |

补充说明：

- **归档不是状态而是公开范围**：一篇稿件的状态仍是“已发布”，只是因超出公开年限（现口径近 3 年公开）不再对前台输出。用 `public_scope` 表达，避免状态与年限纠缠。
- **定时发布**建议放二期：用 `scheduled_at` + 状态 `scheduled` 实现，一期先不做，避免引入定时任务的运维复杂度。
- **回收站 ≠ 日志**：回收站里的稿件可以恢复，物理清理需要单独授权；而每一次删除动作在操作日志里永久留痕（≥180 天）。

## 3. 状态流转

```
                  提交审核                审核通过
   （新建）──▶ 草稿 ──────▶ 待审 ──────────────▶ 已发布 ──撤回──▶ 已撤回
               ▲  │          │                    ▲                │
               │  │          │ 退回               └────重新发布────┘
               │  └──────◀ 退回（附意见）
               │              │
               └──修改后重交───┘

   任意状态（除已发布需先撤回）──删除──▶ 回收站 ──恢复──▶ 回到删除前的状态
```

| 流转 | 触发者 | 前置校验 | 记录 |
| --- | --- | --- | --- |
| 新建 → 草稿 | 栏目编辑 | 无 | `created_at`、操作日志 `article.create` |
| 草稿 → 待审 | 栏目编辑 | 标题、正文、栏目、发布时间齐备；有附件时附件可访问 | `submitted_at`、提交人；同时生成编校任务 |
| 待审 → 已发布 | 发布人 | 编校通过（可配置为必须）；正文非空 | `reviewed_at`、`reviewer_id`、`published_at` |
| 待审 → 退回 | 审核人 | 必须填写退回意见 | `review_note`、退回人、时间 |
| 退回 → 待审 | 栏目编辑 | 同“草稿 → 待审” | 新一轮提交记录 |
| 已发布 → 已撤回 | 发布人 | 必须填写撤回原因 | `withdrawn_at`、原因、操作人 |
| 已撤回 → 已发布 | 发布人 | 无（内容未变） | 新的 `published_at` 或保留原时间（见第 8 节待定项） |
| 任意 → 回收站 | 有删除权限者 | 二次确认 + 填写原因；已发布稿件必须先撤回 | `deleted_at`、`deleted_by`、删除前状态 |
| 回收站 → 原状态 | 有恢复权限者 | 在保留期内 | `restored_at`、操作人 |

## 4. 数据模型改动

### 4.1 `cms_article` 增补字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | 枚举扩展 | `draft`／`pending`／`rejected`／`published`／`withdrawn`／`deleted`（保留 `offline` 兼容期，读时按 `withdrawn` 处理） |
| `submitted_at` | datetime | 最近一次提交审核时间 |
| `reviewer_id` | int | 审核／发布人（关联 `sys_user`） |
| `reviewed_at` | datetime | 最近一次审核时间 |
| `review_note` | text | 退回意见或审核备注 |
| `withdrawn_at` | datetime | 撤回时间 |
| `withdraw_reason` | varchar(255) | 撤回原因 |
| `deleted_at` | datetime | 删除时间（软删除） |
| `deleted_by` | int | 删除人 |
| `status_before_delete` | varchar(16) | 删除前状态，供恢复 |

### 4.2 新增版本留痕表 `cms_article_revision`

每次提交、发布、撤回前把当前内容存一份快照，用于事后查证与回滚：

`revision_id、article_id、version_no、action（submit/publish/withdraw/restore）、title、content_html、summary、status、
operator_id、note、created_at`

> 只在状态流转时留版本（不在每次点保存时留），既够用又不至于把库撑爆；需要更细的可按需扩展。

### 4.3 权限动作（`sys_role` 配套）

| 权限码 | 含义 |
| --- | --- |
| `article.edit` | 新建与编辑（范围受 `sys_role_channel` 限制） |
| `article.submit` | 提交审核 |
| `article.review` | 审核（通过／退回） |
| `article.publish` | 发布、撤回、重新发布 |
| `article.delete` | 放入回收站 |
| `article.restore` | 从回收站恢复 |
| `article.purge` | 物理清理（建议只给管理员，且需二次确认） |

### 4.4 权限矩阵（建议的四个基础角色）

| 角色 | 草稿 | 待审 | 退回 | 已发布 | 已撤回 | 回收站 |
| --- | --- | --- | --- | --- | --- | --- |
| 栏目编辑 editor | 写／改／提交／删除 | 只读（可撤回提交） | 改后重交 | 只读 | 只读 | 只读 |
| 审核 reviewer | — | 通过／退回 | 只读 | 只读 | 只读 | — |
| 发布 publisher | — | 发布（代审通过） | — | 撤回／重新发布 | 重新发布 | — |
| 管理员 admin | 全部 | 全部 | 全部 | 全部 | 全部 | 恢复／物理清理 |

> 方案书提到“稿件终审由政协办公室在系统外把关”，系统内的“审核通过”动作应对应到指定账号；线下审批单可作附件上传留档。

## 5. 后台界面调整

1. **左栏**：“内容管理”下增加稿库导航（与栏目导航条同风格）：`全部｜草稿 n｜待审 n｜退回 n｜已发布 n｜已撤回 n｜回收站 n`，数字为实时计数。
2. **列表页**：稿库作为主筛选（替代现在的状态下拉），再叠加栏目导航条、关键词；列表新增“最近动作”列（如“17:32 由 张三 提交”）。
3. **行内动作随状态变化**：草稿→`编辑｜提交｜删除`；待审→`查看｜通过｜退回`；退回→`编辑｜重交｜删除`；已发布→`查看｜撤回`；已撤回→`查看｜重新发布｜删除`；回收站→`查看｜恢复`。
4. **编辑页顶部**：状态徽标 + 当前流转按钮 + 意见／原因输入框；编辑已发布稿件时提示“修改后需重新发布才会生效”。
5. **批量操作**（二期）：批量提交、批量发布、批量删除，逐条写日志。

## 6. 与前台、接口、静态化的衔接

| 环节 | 规则 |
| --- | --- |
| 公开接口 / 站内检索 | 只出 `status = published` 且 `public_scope = public`（已实现，规则不变） |
| 静态化发布 | 发布器按“当前处于已发布”的集合生成页面；撤回或删除后重新发布时，对应静态文件应被清理，`sitemap.xml` 同步剔除 |
| 旧链接 | 撤回稿件的原地址处置见第 8 节待定项，默认按“保留说明页”实现更稳妥 |
| 缓存 | 接口默认 `no-store`（已实现），撤回后前台立即不可见；接入 CDN 后需按稿件粒度失效 |
| 编校 | 提交待审时生成编校任务（`cms_article_proof`），发布前校验编校结论；《智能编校单》编号写入 `report_no` |
| 审计 | 每次状态流转写 `sys_operation_log`（含操作人、IP、原因、前后状态），留存 ≥180 天；删除为软删除，物理清理单独留痕 |

## 7. 存量数据与迁移

| 现有值 | 迁移后 | 说明 |
| --- | --- | --- |
| `draft` | `draft` | 不变 |
| `published` | `published` | 不变 |
| `offline` | `withdrawn` | 语义最接近；迁移后保留 `offline` 兼容读取一段时间 |

旧库导出的 20,705 条历史稿件建议统一按 `published` 入库，`public_scope` 按年限（近 3 年 `public`，更早 `archive`），避免迁移期把历史内容压进待审队列。

## 8. 需要拍板的四个口径

| 序号 | 待定项 | 备选 | 建议 |
| --- | --- | --- | --- |
| 1 | 审核环节设在系统内还是系统外 | A. 编辑提交→发布人直接发布；B. 编辑提交→审核→发布 | 先按 B 建模，若线下终审则系统内只保留一人一岗的“审核＝发布” |
| 2 | 撤回后旧链接怎么处理 | A. 404；B. 410 Gone；C. 301 到所属栏目；D. 保留只读说明页 | 公文类选 D（保留标题与撤回原因），动态类选 C |
| 3 | 回收站保留期 | 7／30／90 天 | 30 天，超期由管理员确认后清理并记日志 |
| 4 | 是否需要定时发布 | 一期不做／二期做 | 二期做，一期先用“保存为待审、人工发布” |
