# 河池政协网 · 开源件选型说明

> 编制日期：2026 年 9 月 11 日
> 结论：**不替换现有自研轻量 CMS，只借成熟件的模型与样式**。
> 检索方式：GitHub REST API（`api.github.com/repos/<owner>/<repo>`）与各项目官方文档站点，检索日期 2026 年 9 月 11 日。

## 1. 背景与约束

后台进入“稿库状态机 + 用户分组权限”阶段时，提出的问题是：这块有没有成熟的模板或开源代码可以直接拿来用。

判断必须建立在现有工程约束上，本次确认到的约束：

| 约束 | 事实 |
| --- | --- |
| 技术栈 | PHP 8.5，自写 PSR-4 加载器，**没有 composer.json**，`backend/src/bootstrap.php` 明确写着“本期不引 Composer，保持零依赖即可跑” |
| 现有规模 | 后端 50 个 PHP 文件，前端 229 个文件 |
| 接口契约 | `docs/api-contract.md` 已定版，五个检查脚本（页面 19／20、接口 47、后台 204、排序 19）在跑 |
| 数据 | 旧库 20,705 条历史稿件待迁移 |
| 交付环境 | 移动云自建，政府项目，需要源码可控与依赖可审计 |

结论依据第 2 节的候选件实测数据：本阶段要补的两件事（稿库状态机、用户分组权限）合计约 2—3 天工作量，而换整站框架的迁移成本远高于此。

## 3. 采用结论

### 3.1 借模型，不引依赖

| 要补的部件 | 借用对象 | 落地方式 |
| --- | --- | --- |
| 稿库状态机 | Symfony Workflow | 照它的 places／transitions／guards／metadata 结构写成本项目的 `HechiZx\Content\ArticleWorkflow`，状态与流转集中一处，**不引 Composer 包** |
| 用户分组与数据范围 | 若依 RuoYi | 借“角色按机构划分数据范围”的模型（其 README 第 40 行），落成 `sys_role_channel` 的栏目范围，**代码不通用（Java）** |
| 权限码 | php-casbin | 本项目权限码固定 11 个、角色 4 个，自研 `sys_role_permission` 表即可，不引 RBAC 引擎 |

### 3.2 界面皮后置

Tabler 与 AdminLTE 都是 MIT、纯前端资源，替换 `backend/public/assets/admin.css` 不涉及 PHP 改动。本次**没有做**这一步：稿库与权限的功能改动会连带调整列表、按钮与状态标签，先换皮等于改两遍。等功能稳定后再单独做一次视觉改版。

### 3.3 政务前端设计系统的边界

govuk-frontend 与 USWDS 是英、美两国政府的设计系统，可借的是无障碍规范、组件化拆分与配色对比度做法；**版式不能照搬**，中国政务网站另有版式与标识要求。

## 4. 备选方案与取舍

### 方案二：Laravel + Filament + spatie/laravel-permission

- 收益：后台增删改查、角色权限、表单校验开箱即用，开发速度最快。
- 代价：现有 50 个后端文件全部重写，引入大量 Composer 依赖，与政府项目的依赖审计要求要重新对口径。
- 什么时候是对的：如果项目从零开始，且允许引入框架，这是最省力的起点。

### 方案三：换成 Drupal／Plone／October 一类成品 CMS

- 收益：内容审核、版本、权限、审计全部现成。
- 代价：20,705 条旧数据重新迁移、8 种栏目标版式重做、接口契约重写，还要重新培训使用方。
- 什么时候是对的：如果需求升级成“多单位、多站点、上百账号的集约化平台”，自研轻量 CMS 会到天花板。

## 5. 本次落地结果

按方案一实施后已具备：

1. `database/migrations/{mysql,sqlite}/002_workflow_and_permission.sql`：稿库状态字段、用户分组字段、`sys_role_permission` 表、四个内置角色与权限码、存量 `offline` 归一为 `withdrawn`。
2. `HechiZx\Content\ArticleWorkflow` 与 `HechiZx\Content\Permissions`：状态与权限码集中定义。
3. 后台：稿库导航条（带计数，替代状态下拉）、行内流转动作、编辑页流转区（退回／撤回必填意见）、回收站软删除与恢复。
4. 后台：用户管理、角色与权限（权限码勾选 + 栏目范围勾选）、操作日志页。
5. 权限生效点：稿件新建／编辑／流转、栏目管理、一键发布、用户与角色管理、操作日志，均按权限码校验；数据范围按 `sys_role_channel` 过滤。

## 6. 本结论失效的条件

- 需求升级为多单位、多站点、上百账号的集约化平台，自研的状态机与权限模型撑不住时，应回到方案三重新评估。
- 团队后续引入 Composer 并接受第三方依赖，Symfony Workflow 与 Casbin 可以直接接管，届时本项目自己的状态机可以平滑替换（接口形状一致）。
- 若维护方没有 PHP 人员，长期维护能力比技术选型更关键，此时应优先考虑成品 CMS 而非自研。
