> 编制日期：2026 年 9 月 11 日
> 配套文档：`docs/稿库与内容状态设计.md`（稿库状态机是本文的调用方）
> 现状依据：`database/migrations/sqlite/001_init.sql`、`backend/src/Admin/Auth.php`、`backend/src/Admin/AdminController.php`、`backend/routes/admin.php`、`backend/bin/user.php`
> **落地状态（2026-09-11）**：第 3 节“同步做（骨架）”已实现——`sys_user` 补部门等字段、`cms_article` 补 `created_by`／`updated_by`、`sys_role_permission` 建表并写入四个内置角色的权限码、后台新增用户管理与角色与权限页、稿件与栏目动作按权限码校验并按 `sys_role_channel` 过滤数据范围。第 3 节“后置做（增强）”与第 5 节的菜单级权限、统一身份认证仍未做。

结论先说：**用户分组该同步做，但要分清“同步做什么、后置做什么”。** 同步的是数据模型与最小可用分组，后置的是组织架构树、菜单级权限、单点登录这类重工程。

## 2. 为什么建议同步做

1. **稿库上线后没人可分权，状态机就是空转。** 稿库 P0 会产生“谁提交、谁审核、谁发布、谁撤回”四类动作，但目前只有一个管理员账号能登，四个动作堆在同一个人身上，等于自己写、自己审、自己发。政务网站内容管理通行做法是责任到人与岗位分离，这一条没账号体系就落不了地。
2. **稿库的字段本身就是“人”的字段。** `reviewer_id`、`submitted_at`、`deleted_by` 这些都要关联 `sys_user`，如果先上状态机、后补人员体系，迁移脚本、列表页、计数逻辑、检查脚本都要再改一遍。
3. **代价很小。** 建表和仓储都现成，缺的是字段补全、角色落数据、页面上墙与动作校验，属于在既有骨架里填内容，不是另起一套。
4. **反过来才贵。** 等数据录进生产库再补 `created_by`，历史稿件的归属只能靠猜，补不回来。

## 3. 分档：同步做与后置做

| 档 | 内容 | 时机 |
| --- | --- | --- |
| 同步做（骨架） | `sys_user` 补部门等字段、`cms_article` 补 `created_by`／`updated_by`、4 个基础角色落数据、角色绑栏目、账号与角色的后台页面、稿件动作按权限码校验 | 与稿库 P0 同批或紧随其后 |
| 后置做（增强） | 多级组织架构树、用户组套用户组、跨站点授权、菜单级与按钮级权限、单点登录（政务钉钉／统一身份认证）、操作日志看板 | 稿库 P2 之后 |

不建议把“用户分组”整体推到二期：二期本来是定时发布、编校强制前置这类内容侧工作，权限一旦拖到那时，前面的稿库流转全程都是无权限状态在跑。

## 4. 模型设计

### 4.1 分组分两层

- **权限分组 = 角色**：一个用户可挂多个角色，角色决定“能做什么”（权限码）。
- **组织分组 = 部门**：一个用户属于一个部门，用于列表筛选、值班排班，不参与鉴权判断。

这样分的好处是：鉴权只看角色，部门调整不影响权限，避免“用户组”既当组织结构又当权限载体带来的混乱。若后续确有多级单位需求，再引入 `sys_dept` 独立表，先不预支复杂度。

### 4.2 表改动

| 表 | 改动 | 说明 |
| --- | --- | --- |
| `sys_user` | 增 `dept`、`mobile`、`email`、`remark`、`pwd_changed_at` | 部门先用文本字段，可枚举可排序 |
| `sys_role` | 增 `is_system`、`sort_no`、`remark` | `is_system=1` 的内置角色不允许改权限码 |
| `sys_user_role` | 沿用 | 用户与角色的多对多 |
| `sys_role_channel` | 沿用 | 角色的数据范围＝能管哪些栏目 |
| 新增 `sys_role_permission` | `role_id` + `perm_code` | 角色与权限码的多对多 |
| `cms_article` | 增 `created_by`、`updated_by` | 关联 `sys_user`，配合稿库的 `reviewer_id`／`deleted_by` |

权限码固定在代码里定义（避免管理员在页面上乱勾产生语义不明的新权限），角色页只做“勾选已有权限码 + 勾选栏目”。

### 4.3 权限码清单

内容侧沿用 `docs/稿库与内容状态设计.md` 第 4.3 节：`article.edit`、`article.submit`、`article.review`、`article.publish`、`article.delete`、`article.restore`、`article.purge`。

后台功能侧另加：`channel.manage`（栏目管理）、`home.manage`（首页导航栏目、头条轮换、其他栏目与站内横幅维护）、`publish.run`（一键发布／重新生成静态页）、`user.manage`（用户与角色管理）、`log.view`（操作日志查看）。

### 4.4 四个基础角色与数据范围

| 角色 | 权限码 | 数据范围（栏目） |
| --- | --- | --- |
| 栏目编辑 `editor` | `article.edit`、`article.submit`、`article.delete` | 角色绑定的栏目 |
| 审核 `reviewer` | `article.review` | 角色绑定的栏目 |
| 发布 `publisher` | `article.publish`、`article.restore`、`publish.run` | 角色绑定的栏目 |
| 管理员 `admin` | 全部权限码 | 全部栏目 |

数据范围的两条落地规则：

1. 列表、计数、详情都按“用户所有角色绑定栏目的并集”过滤，管理员不受限。
2. 越权访问统一返回无权限提示页（不泄露稿件是否存在），并写 `sys_operation_log`。

### 4.5 待定：编辑能改本栏目全部还是只改自己写的

建议先按“本栏目全部”实现，理由是本级编辑通常互为备份，值班期间需要能接手他人稿件；如果实际要求责任到人更严，再切换为“仅本人创建（审核岗可代改）”，届时加一条数据范围开关即可。

## 5. 后台界面

1. **左侧菜单新增“系统管理”**：用户管理、角色与权限、操作日志（操作日志页可选，数据已在 `sys_operation_log` 里）。
2. **用户列表**：账号、姓名、部门、角色、数据范围、状态、最后登录；动作：编辑、重置密码、停用／启用。
3. **角色页**：基本信息 + 权限码勾选 + 栏目勾选（复用现有栏目导航条的样式与顺序，保持与稿库导航一致）。
4. **重置密码**：管理员设置新密码，或生成一次性初始密码；建议首次登录强制改密，`pwd_changed_at` 为空即视为未改。
5. **顶栏**：显示“姓名（角色）”，替换现在的纯账号展示。
6. **稿件列表与编辑页**：新建时自动写入 `created_by`，编辑时刷新 `updated_by`；无 `article.edit` 权限时不显示编辑入口。

## 6. 推荐排期

| 顺序 | 内容 | 预估 | 依赖 |
| --- | --- | --- | --- |
| 1 | 稿库 P0：状态字段与流转、稿库导航与计数、行内动作、流转写日志 | 1 天 | 无 |
| 1 同批 | 数据模型补字段：`cms_article.created_by`／`updated_by`，`sys_user` 补部门等，`sys_role_permission` 建表 | 半天 | 无 |
| 2 | 用户与权限落地：角色落数据、绑栏目、用户管理页、角色页、动作按权限码校验 | 1.5—2 天 | 第 1 批字段就位 |
| 3 | 稿库 P1 其余项：版本留痕、批量操作、撤回说明页 | 2—3 天 | 第 1、2 步 |

把“数据模型补字段”放进第 1 批，是为了让稿库的 `reviewer_id`／`deleted_by` 和用户的 `created_by` 在同一次迁移里加完，后面只补逻辑、不再动库。
